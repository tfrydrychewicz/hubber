# Hubber

Local, single-user work hub for an engineering manager: a Hono server on Node 26, bound to 127.0.0.1, and a Vite + React web app. Requirements are in `docs/PRD.md`; the plan and the state of each package are in `docs/PLAN.md`.

## Running things

- Node 26 is required; the version is in `.nvmrc`. If `node -v` shows an older one, switch with `nvm use` or put a Node 26 binary first in `PATH`.
- The gate is `npm run check`: lint, type-check and unit tests. `npm run format` fixes formatting and import order.
- When the server, the web app or the build changes, also run `npm run test:e2e`. It builds and starts the app itself, on port 4478 or `HUBBER_E2E_PORT`, on a throwaway workspace that it creates for the run; the browsers come from `npm run test:e2e:install`. The server of the run works under `src/server/egress-observer.ts`, and the run fails when that server did anything that leaves its process: a connection, a name lookup, a started program.
- When the schema or the query of a view changes, also run `npm run perf` and put its result into the package's "Stan" line in `docs/PLAN.md`. It is outside the gate, works on a throwaway workspace of its own and needs about 4 GB of free disk space. At full scale it takes about three minutes on a quiet machine: give the command a timeout of ten minutes. Stopped by a signal it removes its workspace; killed outright it leaves `hubber-perf-*` in the temporary directory.
- `npx tsc --noEmit` checks nothing here, because the root `tsconfig.json` only references the projects. Use `npm run typecheck`.
- Never start the app on the owner's workspace. Every command that creates a workspace or starts the app carries `HUBBER_WORKSPACE` itself, with the same throwaway directory each time, because your shell does not keep an `export` from one command to the next. Create the workspace once with `HUBBER_WORKSPACE="${TMPDIR:-/tmp}/hubber-agent/workspace" npm run workspace:create -- --name Test --kind anthropic` (the command refuses a directory that exists: go on with the one that is there, or remove it first), then put the same `HUBBER_WORKSPACE="${TMPDIR:-/tmp}/hubber-agent/workspace"` in front of `npm start` and of `npm run dev`. Without the variable the three commands exit with code 2 in your session, which they know by `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT` or `AI_AGENT`. That catches a forgotten prefix and nothing else: a workspace that the variable names is opened whoever names it. A start migrates the workspace it opens. Tests take theirs from `createTestWorkspace()` in `src/server/workspace/testing.ts`.
- `npm run synthetic` fills only the workspace that `HUBBER_WORKSPACE` names, never the default one and only an empty one, and migrates it first, like a start.
- A change to the tables is a new file in `src/server/db/migrations`, hand-written SQL with a `--> statement-breakpoint` line between statements, listed in `manifest.json` (first with an empty `sha256` and `schema`), plus the same change in `src/server/db/schema`. A new CHECK, trigger or foreign key gets its case in `src/server/db/guards.test.ts`, with the reason of the refusal; a column built with a builder of `src/server/db/schema/columns.ts` gets its CHECK in the migration; a table gets its line in `src/server/db/schema.types.test.ts` with every column whose type is narrower than text or a number, and a new kind of id its prefix in `src/shared/ids.ts`. The generator writes every table: a new column of a table it writes gets its value in `src/server/db/synthetic/writer.ts`, and a new table gets rows from `world.ts` and `writer.ts`. `npm run check` names what is missing: the tests of `src/server/db` print the manifest entry to paste and say where the Drizzle declaration and the database differ, and the type check names the places in the generator and in the lists of the tests. `npm run db:fixture` then writes the fixture of the new version; while a migration is not on `main`, an edit of its file means pasting its manifest entry again, removing its fixture and writing it again, and a workspace that a start has migrated with the file as it was is refused from then on (exit code 1): remove your throwaway one and create it again, and tell the owner, whose own workspace may have run it. A migration that is on `main` is never edited, renamed or reformatted: workspaces with real data have run it. Only one branch at a time adds a migration.

## Where things live

- `src/server`: the Hono server. `src/server/workspace` is what a workspace is on disk: its place, its configuration file, creating and opening one. `src/server/db` is the application's schema inside the workspace's database file: the SQL migrations and their manifest (`migrations/`), the runner that applies them when a workspace is created or opened (`migrate.ts`), the Drizzle tables for queries (`schema/`), the typed handle (`handle.ts`), the databases of earlier versions of the schema, which the tests of the migrations bring to the newest one (`fixtures/`), the synthetic data generator (`synthetic/`) and the performance scenarios (`perf/`). `src/server/llm` is everything about the endpoint: its address, the credentials, the SDK client and the endpoint diagnostics.
- `src/web`: the React app; its user-facing strings are in `src/web/messages.ts`.
- `src/shared`: what the server and the web app both import: API contracts, identifiers and instants, the folding of names for matching, and the lists of codes that the vocabulary tables of the database hold (`vocabulary.ts`).
- `scripts`: the development runner, the Node version check, the diagnostics command, the command that creates a workspace, the commands that fill a workspace with synthetic data, measure performance and write the fixture of a migration, and the step that gives the end-to-end run its workspace.
- `e2e`: Playwright tests. Spec files take `test` and `expect` from `./fixtures.ts`.
- Unit tests sit next to the code as `*.test.ts` (`*.test.tsx` in `src/web`). A test of a query or of an operation takes its database from `createTestDatabase()` in `src/server/db/testing.ts`: in memory, built by the real migrations, a new one for every test. A test that needs rows takes a filled database from `createSyntheticTestDatabase()` in `src/server/db/synthetic/testing.ts`. A test about the file itself takes a workspace from `createTestWorkspace()`. The reads that `npm run perf` measures and whose plans the tests hold are the list `READS` in `src/server/db/perf/reads.ts`: a view takes its query from there, or changes its entry together with the query.

Node runs the server and the scripts straight from the TypeScript sources, so only erasable syntax is allowed (no enums, no parameter properties) and relative imports carry the file extension. Lint enforces the import boundaries: `src/web` and `src/server` do not import from each other, and `src/shared` imports from neither. Outside tests, `src/shared` and `src/web` use no Node built-in modules, and `src/shared` uses no `window`, `document` or `process`. In `src/server`, `src/shared` and `scripts`, tests and their `testing.ts` helpers aside, only `src/server/workspace/database.ts` imports `better-sqlite3`, and only by that name, with no entry of the package below it (such as `better-sqlite3/darwin-arm64`), only `src/server/llm/client.ts` builds an SDK client, and nothing calls `fetch` or opens a `WebSocket` or an `EventSource`: the client reaches the pinned endpoint over connections of its own, made with `node:http` and `node:https`. The endpoint diagnostics (`src/server/llm/diagnostics`, `scripts/diagnose.ts`) are the one exception: they build a client of their own and call `fetch`. Application code imports no test, no `testing.ts` helper and not `src/server/egress-observer.ts`; `scripts/e2e-workspace.ts`, a tool of the tests, may. Node's modules for the network and for starting programs (`node:http`, `node:https`, `node:net`, `node:child_process` and their kin) are for the files listed in `scripts/lint-boundaries.test.ts`, and a new use goes on that list with its purpose. `src/web` imports no `better-sqlite3` either, and application code imports a package by its name, never by a path into `node_modules`. Lint reads the literal name in `import`, `import()` and `require()`: it sees a function made by `createRequire()` only under the name `require`, and it does not see an `import()` of a computed text or a package named in another letter case. A test helper that is kept as a file is named `*.test.ts` or, under `src/server`, `testing.ts`; under another name the linter and the scans treat it as application code. Only `src/server/db/handle.ts` imports Drizzle's driver (`drizzle-orm/better-sqlite3`), because the driver opens a database by itself when it is given a path. `src/shared` and `src/web` import no `drizzle-orm`. Nothing that creates or opens a workspace (`src/server/workspace`, `src/server/db/migrate.ts`) loads `drizzle-orm`. States that a partial index names are written as SQL text, with the fragments of `src/server/db/schema/predicates.ts`, never bound as parameters. No statement uses `OR REPLACE`, and no foreign key has an action.

## Conventions

- User-facing text is Polish: the interface, the messages of the server and the scripts, `README.md` and `docs/`. Code, comments and test names are English.
- The repository is public. Keep employer names, internal hostnames, model catalogues of private endpoints and personal data out of files and commit messages. Where an example host is needed, use `router.corp.example`.
- Never read or commit `.env` or the top-level `diagnostics/` directory (`src/server/llm/diagnostics` is source code).
- A statement built with Drizzle runs only when it ends in `.run()`, `.all()`, `.get()` or `.values()`. One that does not is silent: no error, nothing written, and neither lint nor the type check sees it. Never end one in `.execute()` and never await one: both throw where the statement stands, with an error that names the four endings, because `src/server/db/handle.ts` puts that refusal on Drizzle's statement classes for the whole process when it is loaded; without it `.execute()` hands back a promise on this driver, so a refusal of the database is not thrown where the statement stands and the write can happen after its transaction has ended. A transaction body is a plain synchronous function that calls no async helper, and its `Tx` is not used after the body has returned. Lint reports a dropped promise only in the application code of `src/server` and `scripts`, and only where it can tell that a call gives one, such as a call of an async function of the repository or of the SDK client; it says nothing about `.execute()` of a statement that a handle builds, which the handle refuses only when the statement is reached, about a promise from Node's own modules or from a Hono request, nor in `src/web` and `src/shared`. A promise that is meant to go is let go with `void`.
- Commit only when the owner asks.
